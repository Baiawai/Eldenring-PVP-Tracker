# Construction et examen Store

La préparation actuelle ne constitue pas une version prête à soumettre. L'ancien classement distant reste désactivé. Le code Store en préparation utilise exclusivement `https://eldenringpvp.com` pour le nouveau classement et ignore les autres adresses configurées localement ; la participation nécessite un consentement et une connexion Steam vérifiée. Dans l'application, les profils du classement s'affichent après acceptation des conditions. Les opérations en attente sur un ancien serveur restent conservées et ne sont pas envoyées depuis la version Store. Le tag GitHub `v1.0.3.0` et les packages déjà construits peuvent différer de ce code : vérifier le contenu et la version du package réellement soumis avant de rédiger ses notes. La version Store utilise le ping Steam lorsqu’il est disponible sans demander d’élévation pour cette mesure. La mesure avancée avec élévation éventuelle concerne uniquement la version de développement. Vérifier les droits sur les ressources du jeu, les images, polices, données et toutes les licences des dépendances redistribuées, notamment les DLL Tesseract.

Sur Windows x64, installer Python 3.15, créer `.venv`, installer `requirements.txt` puis `pyinstaller==6.22.3`. Installer le SDK Windows avec MakeAppx. Exécuter `.\.venv\Scripts\python.exe store\prepare_tesseract.py` pour préparer Tesseract 5.5.4 et ses dépendances dans `build/tesseract-5.5.4` : le développement et la compilation Store utilisent tous deux cette distribution en priorité. Sinon, le script utilise `C:\Program Files\Tesseract-OCR` ; `-TesseractDir` permet de choisir une autre distribution complète avec ses licences. Les modèles OCR du projet sont embarqués. La compilation n'inclut pas les captures personnelles présentes dans `application`.

Au démarrage puis toutes les dix minutes, une installation signée par le Microsoft Store demande si une mise à jour du package principal est disponible. Microsoft limite cependant les vérifications effectives (au plus une toutes les 30 minutes et dix par période de 24 heures) et peut renvoyer un résultat en cache : la détection d'une nouvelle version n'est donc pas garantie en dix minutes. Si une mise à jour est confirmée, le suivi s'arrête après le combat en cours, puis le tracker affiche un écran obligatoire avec un lien vers sa fiche Microsoft Store. Une erreur, une indisponibilité du Store ou une expiration du délai laisse l'application accessible hors ligne ; une mise à jour déjà confirmée reste obligatoire. La version de développement et les packages non signés par le Store ne sont pas concernés. Tester cette fonction avec une installation Store réelle avant publication. [Limites de l'API Microsoft Store](https://learn.microsoft.com/en-us/uwp/api/windows.services.store.storecontext.getappandoptionalstorepackageupdatesasync).

L'écran indique la version installée et, si possible, celle proposée. Si Windows ne fournit pas le numéro de la mise à jour, un module local facultatif peut consulter la dernière version publiée au Store et l'afficher comme valeur indicative : elle peut différer de la version proposée sur l'appareil. Cette recherche est effectuée en arrière-plan seulement après confirmation d'une mise à jour ; elle ne décide jamais du blocage et son absence ou son échec ne le modifie pas. Le bouton ouvre le Store et ferme le tracker sans fermer l'onglet.

Après réservation du nom dans Partner Center, reprendre exactement le nom d'identité du package, le sujet Publisher et le nom d'éditeur communiqués par Partner Center :

```powershell
.\store\build.ps1 -Identity 'IDENTITE_PARTNER_CENTER' -Publisher 'CN=SUJET_PARTNER_CENTER' -PublisherDisplay 'NOM_EDITEUR' -Version '1.0.11.0'
```

La version par défaut du script est `1.0.11.0` ; avant une soumission, vérifier dans Partner Center que le numéro choisi est supérieur à celui de la version déjà publiée. Le script vérifie avant compilation que la version passée en paramètre correspond à `application/version.py` et aux métadonnées Windows de l'exécutable ; la quatrième composante doit être zéro pour le Store. Le fichier MSIX non signé est créé dans `dist/store/`. Les options `-OutputDir` et `-WorkDir` permettent de construire dans des dossiers séparés pour conserver les paquets précédents. `-ExecutableOnly` construit uniquement l'exécutable et ses ressources. Une signature de test et un certificat approuvé sont nécessaires pour tester l'installation sur une machine ordinaire ; Microsoft signe le package publié après certification. Tester l'installation, le démarrage, les mises à jour, la désinstallation, les modes de suivi et la capture en plein écran avec Steam et le jeu avant la soumission. Ne pas lancer l'exécutable parallèlement à un tracker actif, car les deux utilisent le port 5000.

Le tracker essaie d’ouvrir `http://elden-tracker.localhost/` avec une écoute exclusive limitée à `127.0.0.1:80`, en conservant `127.0.0.1:5000` pour les anciennes sessions. Si le port 80 est occupé, il ouvre `http://elden-tracker.localhost:5000/`. Le mode fenêtre dédiée nécessite Chrome ou Edge. Vérifier l’accès dans le navigateur, le repli lorsque le port 80 est occupé, la reprise des préférences locales et les deux modes d’ouverture dans le package Store installé.

Le contrôle `.\.venv\Scripts\python.exe store\smoke_test.py` utilise un APPDATA temporaire et interroge l'interface sans ouvrir de port. Il nécessite l'accès à WMI ; il ne remplace pas un essai de capture en jeu ou du package installé.

Renseigner la fiche Store, ses captures et une URL publique de politique de confidentialité. Celle-ci doit décrire les captures d'écran, les données conservées localement (dont historique Steam et adresses IP éventuelles), et l'identifiant construit à partir de l'adresse MAC et du nom de machine. Vérifier les données effectivement transmises, leurs destinataires et durées de conservation. L'application utilise un serveur HTTP sur localhost et possède des routes de modification : examiner leur protection contre les requêtes non sollicitées d'autres pages locales ou sites web avant publication. L'installation MSIX peut isoler ou rediriger les données existantes : tester la migration et la désinstallation sur une copie, sans toucher aux données réelles.

## Préparer les textes de la fiche

Les brouillons [descriptions](descriptions-fiche-1.0.10.0.md) et [notes de version](notes-de-version-1.0.11.0.md) couvrent les 30 langues de l’interface. Les notes Store sont un résumé court ; les [notes GitHub](../release/github-notes-1.0.11.0.md) comportent des détails supplémentaires en français. Les textes doivent être relus et comparés avec la dernière version effectivement publiée avant toute soumission.

Pour préparer un fichier de travail, exporter d’abord les fiches **MSIX** depuis Partner Center, puis fournir cet export CSV UTF-8 à l’outil local :

```powershell
.\.venv\Scripts\python.exe store\prepare_listing_csv.py 'partner-center-export.csv' 'partner-center-brouillon-1.0.11.0.csv'
```

L’outil crée uniquement le fichier de sortie, qui ne doit pas déjà exister ; il ne modifie pas l’export et n’envoie ni n’importe rien. Il vérifie l’en-tête `Field,ID,Type,default` ou `Field,ID,Type (Type),default`, refuse les colonnes essentielles ou les deux lignes cibles manquantes, ainsi que les données ambiguës ou mal formées. Les types `Text` et `Texte` sont acceptés pour les deux champs. Il conserve les valeurs `Field`, `ID`, `Type`, `default` et les autres cellules, puis remplit uniquement `Description` et `ReleaseNotes` dans les 30 colonnes correspondant exactement aux langues du manifeste, comme `de`, `fr`, `en`, `zh-Hans` et `zh-Hant`. Le code indonésien `id` est traité comme une colonne de langue distincte de la colonne technique `ID`. Les colonnes de ces langues qui manquent à l’export sont ajoutées ; les autres champs y sont laissés vides. Lorsqu’une variante explicitement associée au brouillon existe déjà, comme `fr-FR`, `en-US`, `de-DE`, `zh-CN` ou `zh-TW`, ses deux champs sont aussi mis à jour ; aucune colonne de variante régionale supplémentaire n’est créée. Les autres variantes et champs existants restent inchangés. Les limites sont contrôlées à 10 000 caractères pour la description et 1 500 pour les notes.

Pour préparer un dossier d’import séparé avec les images localisées, utiliser explicitement l’option `--bundle`, le nom de produit souhaité et le dossier contenant les captures :

```powershell
.\.venv\Scripts\python.exe store\prepare_listing_csv.py 'partner-center-export.csv' 'StoreDraft-1.0.11.0' --bundle --title 'Elden PVP Tracker' --screenshots 'CHEMIN_VERS_CAPTURES_LOCALISEES'
```

Le dossier de sortie doit être nouveau, et son nom doit utiliser des lettres ASCII, chiffres, points, traits d’union ou soulignés. Il contient un seul `listing.csv` et les PNG copiés nécessaires. L’outil ne renseigne `Title` et `DesktopScreenshot1` à `DesktopScreenshot4` que si la cellule de la langue est vide ; les titres et URL d’images déjà présents sont préservés. Chaque PNG copié est vérifié (format et dimensions) et les chemins dans le CSV incluent le nom du dossier racine, comme demandé pour l’import d’un dossier. Aucun fichier existant n’est écrasé. Les captures proviennent d’une interface de démonstration et doivent être revues avant soumission ; elles ne sont pas issues d’une installation MSIX réelle.

**Relire l’ensemble du dossier et son aperçu dans Partner Center avant tout import.** Microsoft peut utiliser la colonne `default` quand une cellule linguistique est vide ; de nouvelles colonnes peuvent créer de nouvelles fiches exigeant notamment un titre et une capture. Vérifier les variantes de langue et de marché, les titres, images, URL, éventuelles bandes-annonces et tous les champs par défaut : l’outil ne garantit pas l’acceptation du fichier. Il ne remplace ni la relecture des traductions ni la vérification des droits. L’import éventuel reste une étape manuelle distincte.
